## 1. Outcome

`github_attestation` approval-source mode may be enabled on a real GitHub connection only after, in this order:

1. Cloud ships the production admission path behind the `native` default: a mode-aware installation permission audit (A0), a proposal-exposure writer (`github_proposal_exposures`, A1), a webhook-driven observation request (A2) and a worker that observes, admits, republishes the Check (A3) — each a vertical slice with vitest + pgTAP acceptance tests, failing closed.
2. The wired path has produced a `satisfied` attestation end to end through real GitHub webhooks on the owner's controlled repository, **and that attested proposal has been promoted** by a service-role `promote_github_attested_proposal_candidate_v1` call made by the operator (Q1 step 8; promotion is not part of the webhook path), with the live provider responses retained as a sanitized fixture that the unit mocks replay (Q1), the `<slug>[bot]` lookup proven live (Q2) and every fail-closed predicate triggered live (Q3).
3. A retained evidence record and per-connection go/no-go checklist exist (Q4) and every §11 item has an owner-signed disposition (Q5).

**Exclusions.** No customer repository. No hosted database of any kind: SQL-side verification and the live webhook runs both use a local `supabase db reset` database (`supabase_db_cloud`) served by a local `next dev` behind a tunnel (§3 E9, D-10). Never the production or Preview projects. No support for CODEOWNERS-required branches or rulesets (D-1; both stay fail-closed). No change to the exact protection matrix. No automatic promotion: neither promotion RPC has a production caller today, and wiring one is a product change outside D-1…D-14; Q1 proves promotion by a service-role call inside the window (§5 Q1 step 8).

## 4. Design decisions

- **D-A Minimal wiring, existing seams.** No new transport. Exposure is written inside the existing publication receipt; admission enters through the existing webhook route; observation runs in a worker shaped like `github-check-retries`. Each stays a no-op while the repository's policy mode is `native` (fail closed on missing policy: `gate.policy_missing` stays the SQL answer).
- **D-B Exposure = the published assessment Check.** The reviewer's exposure is the `AgentDoc Gate` check run that assessment publication records; `published_reference` = `p_details_url`, `published_digest` = `p_rendered_request_digest` (`github-check-publication.ts:723-729`). Writing it in `record_github_check_publication` keeps exposure and receipt atomic and reuses the trigger's ingestion join. The insert is idempotent on the table's unique key (`on conflict … do nothing`), so re-publications on the same head keep the first `created_at` (P1 M-4 / QP1-M3).
- **D-C Admission is queued, not inline.** GitHub expects a webhook response within 10 seconds (external fact, **unverified** here); the observer may take up to 60 s. The webhook route only records a pending observation request, in the same transaction as the delivery row (P1 M-1 / QP1-M1); a separately invoked worker route observes (D-11). Queue latency budget: unbounded before the observer (the observer starts its own clock, `:399`) and irrelevant to the window; the budget that matters is after the snapshot (D-I).
- **D-D Republish through the assessment trigger (verified, P1 H-3 / QP1-M2).** After an attestation or attempt is recorded, the worker calls `publishGitHubCheck({kind:"assessment", workspaceId, repositoryId, principalId, changeRequestSystem:"github_pull_request", changeRequestId: String(prNumber), headSha})`, because `prepare_github_check_publication` is the only RPC that dispatches on the committed mode and selects the current attestation (`20260921014000…:854-912`). Adding an attested branch to `prepare_github_check_publication_for_approval` was rejected: it would duplicate the dispatcher, the retry queue is already keyed on assessment-shaped rows (repository, principal, gate decision), and `_for_approval` is a native-only wrapper by design (`20260921000000…:573`). `principalId` is the `principal_id` of the latest `github_check_publication_receipts` row for (repository, PR, head) — the submitting Action principal, whose `github_installation_submission_principals` row the private twin requires (`:747-756`).
- **D-E Recorded fixtures.** Every live run retains raw provider responses (URL, status, body) sanitized (tokens, keys, e-mails, avatar URLs, `node_id`s stripped). A replay test feeds the fixture into the observer's `fetch` mock and asserts the live result, keeping mocks equal to reality.
- **D-F Evidence without secrets** in cloud `docs/operations/qualification/e8.1/` and fixtures in `src/lib/__fixtures__/` (D-4).
- **D-G Rollback is policy, not code.** `record_github_approval_source_policy` mode `native`, per **installation**: every repository bound to the installation records `native`, and because D-13 refuses a mixed installation in both directions, an installation with two or more attested repositories bound cannot roll back in E8.1 at all — a new App installation instead (R-8, R4-3). Q4 (2) therefore verifies before enablement that the attested installation serves a single repository; rollback stays reachable **only while** it still serves one — binding a second attested repository later is admitted without warning and gives rollback up for good in E8.1 (step (6)(e), R6-2); nothing else is reverted.
- **D-H Time control.** TS `observation_duration` by injected delay; SQL window cases cited to existing pgTAP.
- **D-I Retries restart from observation (P1 H-4).** Attested currentness expires 60 s after `snapshot.completed_at` (`:217`) and the attestation itself must be admitted within 60 s of it (`20260921013000…:383`). No step after the snapshot is retried in place: a failed or `retryable` admission, publication or promotion finalizes the observation request `pending`, and the next claim starts again at A3 step 1 with a fresh permission observation and snapshot. Once step 5 has committed the attestation, the restart cannot mint another for the same review — the unique key `(workspace_id, exposure_id, external_identity_link_id, review_id)` (`20260921010000…:241`) includes the review id, and step 5 would only hit `23505` — so the restart re-publishes the retained attestation while it is current and otherwise records the lapse (A3 steps 2 and 6); a fresh attestation after that needs a re-approval (fresh review id, R2-4) (R10-3). The post-snapshot budget (decision + attestation + publication, and Q1's promotion) is 60 s minus provider latency and minus any wait on the Workspace allowlist key, all inside one worker run. The republish takes the allowlist + source-policy pair exclusive (`20260921014000…:870`), and so does the attestation trigger (`20260921013000…:366`), so while another repository in the same Workspace is admitting an attestation or republishing, this one waits inside the window (R9-2); past it the dispatcher finds no current attestation and publishes the native `gate.approval_missing` decision, which returns `succeeded` like an attested one (§2.3, §11 R10), so A3 step 6 checks which decision the receipt carries and records the lapse instead of finalizing `done` on the outcome alone (R10-3); the observation request lease is 180 s (≥ 60 s observation + 60 s post-snapshot + provider latency) and the finalizer verifies `p_lease_id` as `finalize_github_check_retry` does. The observation request carries the retry. A `retryable` republish still records a failure row, and the failure trigger enqueues a `github_check_publication_retries` row that the worker cannot bypass (§2.3); A3 therefore adds a claim-side rule to the live `claim_github_check_retry` (`20260921000000…:1666-1740`, keeping its pilot-capacity locks, `concurrent_work` reservation and return shape, §2.3): **after** the `pilot-limits:environment` advisory lock (`:1679`) and **before** the `limit 1` selection (`:1680-1684`) — the per-row `pilot-limits:workspace:<ws>` lock (`:1686-1688`) follows the selection, and the bulk pass spans workspaces, so `release_pilot_capacity` (`:492-515`) takes environment → workspace re-entrantly underneath it, the same order as `dispose_github_check_retry` (`:1851-1862`) and `redrive_github_check_retry` (`:1923-1928`); placing the pass before `:1679` would hold retry row locks while waiting for the environment lock (P4 Fable L1) — one bulk `update … set state='superseded', completed_at=clock_timestamp()` (`completed_at` is mandatory for terminal states, `20260919000000…:25`) finalizes every `pending` row whose (repository, change request, head) already has a `github_check_publication_receipts` row newer than the retry's `created_at`, writing each row's `superseded` attempt event as `finalize_github_check_retry` does (`20260919000000…:202-207`) **except** `attempt_number = greatest(retry.attempts, 1)`: a never-claimed row has `attempts = 0` (`:14`) and `attempt_number` must be 1–5 (`:102`), so copying `v_retry.attempts` verbatim would raise 23514 and wedge every claim (P4-M2 attempt number); the lease id is a fresh `gen_random_uuid()` per row so `release_github_retry_execution_capacity` passes its null-lease guard (`:1748-1749`), finds no `concurrent_work` reservation for it (`:1751-1753`) and releases the gate-decision-keyed `queue_depth` reservation (`:1759-1772`, §2.3); the claim then continues to the oldest live row in the same call. A late retry thus never re-prepares behind a fresher publication and, past the window, never overwrites a satisfied attested Check with the native fallback. The rule is mode-independent (in native mode it only skips a redundant re-publication of a head that was already republished) and covers every producer of retry rows, including the Action's own assessment publication under attested mode, which a `publishGitHubCheck` option local to A3 would not.
- **D-J Mode-aware installation audit (D-12).** The native audit's expected set becomes a function of the repository's committed approval-source mode at audit time: `github_attestation` → the seven-grant attestation profile; any other state (`native` or no revision) → the three-grant native profile; anything else is `connect.permission_exceeds_manifest`. One App per connection and **one installation, one mode (D-13)**: the audit never accepts a union or a superset, so an installation bound to two repositories cannot serve one in `native` and the other in `github_attestation`; both writers of the (repository, installation, mode) triple refuse to create a mixed installation, failing closed with the new registered code `connect.installation_mode_conflict` (SQLSTATE `42501`, like its neighbour `gate.policy_missing`; no grant is involved and the connection stays healthy, so `connect.permission_exceeds_manifest` is **not** reused, R2-2): `record_github_approval_source_policy` (E8.1.T4, `20260921013000…:162-203`) refuses a mode change while the repository's installation (`github_repository_installations`, `20260824950000…:1-9`) is bound to another repository whose committed mode differs, and `connect_github_repository_installation` (`20260914002000…:223`) refuses a **new** binding whose repository's committed mode (`native` when it has no revision) differs from the modes already committed on that installation (R2-1); both checks read the sibling modes under a new installation-wide advisory lock `github-installation-mode:<installation_id>` (A0 Files (5)/(6)), taken after the settings lock — throughout this plan, the per-repository source-policy key taken through the helper `private.lock_github_approval_source_policy` that A0 Files (1) extracts (shared by readers, exclusive by the mode mutation), never the Workspace allowlist pair of `lock_github_approval_settings` (R7-4) — and before any per-binding `github-installation:` lock — every shipped `github-installation:` key is per (Workspace, repository, installation) (`20260914002000…:28-32,200-204`, `007000:15`, `011000:38-40`, `005000:72-75`), so it never serializes two repositories on one installation (R4 re-verification, R4-V1) — so a concurrent bind and switch cannot both commit. That lock cannot see the same-repository race — a mode switch on C against a concurrent `connect(C, I)` for an installation C is not yet bound to, unbound or bound elsewhere, because Files (5) locks only the installations C is already bound to — and it does not need to: that race is closed by the settings lock on (Workspace, repository), **exclusive versus shared**, not by the installation-mode lock (R5-1). `record_github_approval_source_policy` takes `github-approval-source-policy:<workspace>:<repository>` **exclusive** (`pg_advisory_xact_lock`, `20260921013000…:176`) right after input validation and the isolation check (`:171-175`) and before its `workspace_repositories` check (`:177`), the idempotent-receipt return (`:186`) and `gate.policy_missing` (`:195`) — around the whole body — and that is the key `lock_github_approval_settings` takes shared (`20260921010000…:165`; exclusive `:168`); A0 Files (2) makes connect take it **shared** (the shipped connect takes no settings lock, only its `github-installation:` locks, `20260914002000…:28,200`), so the switch and the bind serialize and whichever runs second reads the other's committed mode or binding (step (5) pair (g)). The scope is **the installation, across Workspaces** (R3-2): nothing makes `installation_id` unique — the binding key is (workspace, repository, installation) (`20260824950000…:5`) and the per-Workspace webhook URL resolves a delivery by (Workspace, installation, external repository id) (`github-webhooks/route.ts:113-121`) — so one installation may be bound under two Workspaces, and the App's grants are one set for all of them; the sibling read spans Workspaces because both RPCs are `security definer` and so run as their owner, `github_repository_installations` has row level security enabled but **not forced** and carries no policy (`20260824950000…:49-52`; no `force row level security` and no `create policy` names it in any migration, unlike `repository_gate_policies`, `20260905000000…:1841`), and the table and both functions are created by the same migration role (no `alter … owner` and no `set role` in any migration) — the owner is exempt from non-forced RLS (R4-1; `search_path` hardening governs name resolution, not visibility), and the refusal carries the code only, never a sibling's identifiers. There is no unbind — binding rows are immutable (`20260824950000…:38-46`) — so the remedy is **mode-before-bind** (D-13, R3-1): every repository records `github_attestation` before it is bound, and repositories already bound `native` need a new App installation (R-8). The reuse rule (`007000:35-37`) and the retained-pause rule (`:30-34`) compare against the same mode-selected set, and the reuse rule additionally requires the latest audit's own `expected_permissions` to equal it, so a mode switch always forces a fresh audit. The mode is read under the shared settings lock taken **before** the `github-installation:` lock, matching the settings → installation order of the attestation trigger, evaluator and promotion; every other shipped installation-lock holder (the attestation permission observation RPC `20260921011000…:38-40`, the delivery-insert trigger `20260914005000…:72-75`) takes no settings lock at all, and A2 reads the mode before its delivery insert, so no path holds the installation lock while waiting for the settings lock (§2.3, P4-M1). The attestation permission observation (`20260921011000…`) keeps its own exact seven-grant check unchanged — under attested mode both audits expect the same set, so one `/app/installations/{id}` read serves both.

## 10. Risks

- **R-1.** Live `collaborators/<slug>[bot]/permission` may 404 or return a different `user.id` (Q2 measures it; unverified).
- **R-2.** `mergeable` laziness makes the first observation after a push land on `merge_state`; the next A3 claim restarts from observation (D-I).
- **R-3.** The whole post-snapshot chain (decision, attestation, publication, and Q1's promotion) must fit in 60 s; Q1 measures the offsets (D-8). A slow provider makes the window the binding constraint before anything else does; the second consumer is Workspace load, since every attested admission and republish in the Workspace serializes on the exclusive allowlist key (`20260921014000…:870`, `20260921013000…:366`), so several attested repositories that are busy at once lengthen every post-snapshot chain (D-I, R9-2). Qualification cannot measure this, because E1 is one repository on one installation.
- **R-4.** Permission observations are latest-wins per installation (`20260921014000…:218-231`); two concurrent A3 runs for one installation could interleave them. A2's claim leases at most one request per repository at a time, which serializes runs per installation at E1 scale (one repository per installation); documented, not otherwise locked.
- **R-5.** The exposure insert inside the receipt function widens a hot path; it is guarded by mode, idempotent, and covered by the integration harness.
- **R-6.** A retry claimed in the seconds between an A3 republish failure and the observation-request restart re-prepares on its own: inside the window it selects the same retained attestation, past it it publishes the native `gate.approval_missing` fallback and the restart then takes step 6's lapse branch (R10-3); the claim-side supersede rule blocks only the late case. Same shape as any two concurrent publications on one head today; documented, not locked.
- **R-7.** A0 changes what "healthy" means for every future attested connection; the no-revision default keeps every existing native connection unchanged, and the pgTAP in A0 pins that.
- **R-8.** Documented limitation (D-13, mode-before-bind): binding rows are immutable and there is no unbind, so an installation with two or more repositories already bound `native` cannot convert to `github_attestation` in E8.1 — both switches are refused with `connect.installation_mode_conflict` (step (6)(a)). Converting such repositories means a new App installation, bound only after each repository has recorded the mode. The refusal is symmetric, so the same holds for rollback: an installation with two or more attested repositories bound cannot return to `native` in E8.1 (step (6)(a) mirror; D-G is per installation, and Q4 (2) verifies single-repository attested installations before enablement, R4-3); that check holds only at the moment it runs, so rollback stays reachable only while the installation serves one repository — a later second attested bind is admitted and removes it (step (6)(e), R6-2). Any relaxation (installation-wide switch, audited unbind) is a later owner decision, not E8.1.
- **R-9.** Pre-existing deadlock on cloud main (R10-2, §11 R9): `record_github_check_publication_with_capacity` takes `pilot-limits:environment` → `pilot-limits:workspace:<ws>` (`20260921000000…:1012`, `:920-923`) before the body's `assessment-ingestion:` key (`20260914001000…:136-139`), while `prepare_github_check_publication` takes ingestion (`20260921014000…:867`) before its capacity reservation (`:897-900`, natively `20260921000000…:553-555`). Neither key depends on mode, so two concurrent uploads for one pull request, or an upload against the retry worker (`github-check-retries/route.ts:63`, `:83`), can deadlock (40P01) on a plain `native` connection today. Accepted until A1 merges — A1 is the third slice of the stack, so A0 ships with it still present — and fixed by A1's ingestion-first order (A1 Files, pair (j)); reverting A1 restores it (A1 Rollback). A separate earlier fix was considered and not chosen (D-14, decided).
