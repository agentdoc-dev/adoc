## 2. Domain decisions and shared contracts

### D1 — pre-merge approval and the AgentDoc check dependency

**Accepted 2026-09-21.** An open, non-draft, conflict-free PR may supply approval before merge when all independent branch requirements pass. Exclude only the exact configured AgentDoc governance check, identified by publisher App ID plus context `AgentDoc Gate`, from the prerequisite check set. Its own result is the output of the approval gate; requiring it to pass first is circular.

Merged-only admission was rejected because it cannot make a required pre-merge AgentDoc check self-satisfying; deployments requiring that check would need native approval before merge. No wildcard/name-substring exclusion; another App with the same check name remains required. Do not add an exception for any unrelated failed check.

### D2 — Cloud attests evidence; native approval stays human-only

The existing `adoc.approval.v0` requires `principal.type: "human"`. Its table additionally requires a real `auth_session_id`, `approval_command` request binding and native API request foreign keys. Do not widen those constraints or fabricate browser sessions for GitHub reviewers/bots.

Use separate immutable `github_approval_attestations` and `github_approval_attestation_invalidations` tables, Workspace-qualified foreign keys, closed canonical record bytes/digest, and the existing authorization evaluator with `proposal.approve`. A human reviewer maps through E2.3 to an eligible human principal. A bot maps to its actual non-human principal and is rejected unless T4's exact exception applies. Model output never supplies identity, authorization or an approval record.

Gate/promotion consume one explicitly tagged approval reference. Retain native IDs/FKs and add a separate attestation FK with an at-most-one constraint; an approval-dependent pass or promotion requires exactly one current reference, while neither is permitted only for an existing no-approval gate mode or a blocked `gate.approval_missing` decision. Do not introduce a generic approval-provider framework or an untyped polymorphic ID. Use versioned Cloud facts for the changed shape; old native v0 bytes/routes remain decodable and unchanged.

### D3 — approving a Proposal Set is more than approving a commit

Cloud must already hold the exact Proposal Set, scope, surfaced Proof Obligations and source binding. Retain a server-authenticated proposal exposure record before the qualifying review: Workspace, repository ID, PR number, head SHA, proposal version/digest, obligation snapshot, and the server-published proposal reference/digest. The visible reference leads to the exact immutable proposal details. Review submission must be after that exposure and name that head. An old code review cannot be attached later to a different generated Proposal Set.

Use the existing proposal-ingestion/check-publication path to publish and retain this binding. A webhook or mutable Action comment may trigger a refresh, but cannot provide authoritative approval facts. Do not require E8.2's future knowledge-PR reference block; this is the minimum binding for E8.1's current source PR. Duplicate exposure of unchanged bytes is idempotent; changed proposal/obligation bindings require a new exposure and qualifying review.

### D4 — two different kinds of currentness

1. **Semantic approval validity:** exact current proposal-set digest and current blocking obligations, using E5.2 rules. Semantic content changes append invalidation; source placement alone does not.
2. **GitHub evidence validity for a current decision:** exact observed PR/head, current non-dismissed review, current identity/permissions/settings, readable applicable protection and satisfied checks/owners/merge requirements. A retained semantic approval is not proof of a new GitHub head.

A placement-only commit therefore preserves the semantic approval record but requires a newly verified head binding before an attested current-head gate can pass. Keep these reasons separate in display and tests. A stale head is `attestation.binding_mismatch`, not a fabricated semantic-change event.

Use a bounded observation window and fresh provider read before admission and each consequential attested gate/promotion decision. Proposed initial maximum observation age: 60 seconds, server-controlled and tested with injected time. Expired/unavailable data blocks new authority; it does not erase historical records. GitHub and PostgreSQL cannot share an atomic transaction: record the observation interval, recheck the PR head/review/rules fingerprint before commit, and reject changes. Do not claim absolute protection from a provider mutation after the final read. Relevant webhooks trigger refresh/invalidation; missing webhooks cannot allow indefinite positive caching.

### D5 — exact settings, ordering and least privilege

Keep native mode as default. Add a per-repository approval-source policy (`native` or `github_attestation`) using the existing `policy.manage` authorization and receipted policy mutation pattern; mode is distinct from the four governance levels. Selecting a mode grants no reviewer permission and cannot bypass an existing blocking obligation. T4 keeps bot entries out of that repository policy: per PRD §15.2 and GOV-002 they live in one Workspace-scoped governed bot allowlist, mutated under the same `policy.manage` authorization at Workspace scope and the same receipted pattern, not a separate permission engine. One entry serves every repository in the Workspace, and one receipted revision revokes it everywhere. An entry has effect only in a repository whose current mode is `github_attestation`.

At attempt start, persist the current committed repository mode revision and Workspace allowlist revision under the Workspace allowlist lock then the repository policy lock (always that order), then release both before GitHub network reads. Mode writers take the repository lock, allowlist writers the Workspace lock, and attempt creation and admission take both, so every settings write serializes with attempts. Admission uses those frozen revisions; a concurrent addition is invisible to the attempt. Recheck current restrictive revocations, identity/source ACL and mode at commit; a later removal must not remain usable through an older permissive snapshot. Receipt, audit and setting become visible in one transaction. Reject any admission trying to consume a setting written in its own transaction; test direct RPC/SQL paths too.

Named identity means `(provider, issuer, immutable GitHub actor ID)`, scoped to the Workspace; retain login only for display. No wildcard, organization-wide rule or login-only matching. An allowlist only lifts the non-human-type rejection. The principal still needs `proposal.approve` and every binding, review and branch requirement.

### D6 — rework decisions

**Accepted 2026-09-23/24** while cloud#169 was reworked against this plan. Each is built and pinned in the owning bullet (T1, T3, T5).

1. **Break-glass under `github_attestation` is refused.** A gate emergency receipt, like a native approval, cannot authorize a gate while the repository's current mode is `github_attestation`: the gate-decision insert trigger refuses with `governance.attestation_not_current` (SQLSTATE `42501`) and retains no decision. Operators switch the repository to `native` first (a receipted mode change), then record the receipt. Within the trigger's non-attested branch (`approval_kind` distinct from `github_attestation`), the guard fires on `approval_id` or `emergency_receipt_id`, because an emergency-only decision has no approval kind.
2. **The satisfied projection names non-human approvers.** A gate pass driven by an allowlisted bot attestation publishes its reviewer with the actual `service`/`agent`/`workload` type; the attestation is the authority, the projection only names it. The Action's human-only satisfied rule in `compose.sh` is relaxed in action#68 (release v2.0.0-alpha.21 pending); until it ships, the Action renders a bot-satisfied projection as unavailable, which grants nothing.
3. **An unlinked GitHub `Bot` attempt projects `principal_type: "service"`.** The attempt binds the immutable GitHub actor ID with a null identity link, and the table constraint confines that shape to `rejected`/`bot-rejected`, so the projection's fixed `service` type cannot describe any other row.
4. **`bot_allowlist_revision_id` is null until the Workspace's first allowlist revision.** The record type below is `string | null`; both freeze comparisons treat null as equal to null, and `github_bot_approval_allowlist_has_entry` returns false for a null revision, so a Workspace with no allowlist admits no bot. The repository mode revision is never null: a human attempt in a repository with no retained mode revision is refused typed (`github_approval_attestation.invalid`, SQLSTATE `23514`, not a registry code) and retains no record or attempt.

### Contract vocabulary and proposed types

The following are **proposed interfaces**, not existing exported functions. Each owning slice freezes its exact schema names/fields across repositories before consumers implement them: T1 the stored record and result union, T3 the attempt envelope, T5 the gate-fact and `.v1` envelopes (see T1's implementation sequence).

```ts
type AttestationStatus =
  "satisfied" | "bot-rejected" | "binding-mismatch" | "requirements-unmet";

type ApprovalReference =
  | { kind: "native"; approval_id: string; record_digest: string }
  | {
      kind: "github_attestation";
      attestation_id: string;
      record_digest: string;
    };

// Each failure status carries exactly one code; Cloud validates the pair.
type AttestationFailure = (
  | { status: "bot-rejected"; code: "attestation.bot_approver_rejected" }
  | { status: "binding-mismatch"; code: "attestation.binding_mismatch" }
  | { status: "requirements-unmet"; code: "attestation.requirements_unmet" }
) & {
  failed_predicates: readonly string[]; // closed enum in the actual schema
};

// Accepted records require every field; failures live in a separate attempt log.
type GitHubApprovalAttestation = {
  schema_version: "agentdoc.cloud.github_approval_attestation.v0";
  attestation_id: string;
  workspace_id: string;
  repository_id: string;
  pull_request_number: number;
  head_sha: string;
  proposal: { version_id: string; proposal_set_digest: string };
  exposure_id: string;
  reviewer: {
    principal_id: string;
    external_identity_link_id: string;
    github_actor_id: string;
    principal_type: "human" | "service" | "agent" | "workload";
  };
  review: {
    id: string;
    commit_id: string;
    state: "APPROVED";
    submitted_at: string;
  };
  scope: readonly ScopeEntry[]; // reuse native scope representation
  proof_obligations: readonly ProofObligationRecord[];
  policy_revision: string; // evaluation-rule version, not a settings revision
  approval_source_policy_revision_id: string; // repository mode revision frozen at attempt start
  bot_allowlist_revision_id: string | null; // Workspace allowlist revision frozen at attempt start; null until the first revision (D6.4)
  authorization_decision_id: string;
  observation: {
    snapshot_id: string;
    digest: string;
    started_at: string;
    completed_at: string;
  };
  requirements: {
    // Stays eight booleans as built. The shipped write|admin collaborator
    // permission check is a sub-condition of identity; its failure name
    // `review_permission` is an evaluator result string, not a field here.
    identity: true;
    review: true;
    codeowners: true;
    checks: true;
    protection: true;
    head: true;
    proposal: true;
    merge: true;
  };
};
```

The `principal_type` union matches Cloud's `20260824000000_create_workspace_memberships.sql`: human, service, agent and workload. Retain the actual non-human provenance rather than coercing to human. Workload-backed reviewers remain subject to their current delegation/evidence constraints; the bot exception cannot create or extend a workload session. A TypeScript type alone is insufficient: strict runtime decoder and database fact validator must reject missing/extra/false fields, malformed IDs/digests/times and record/column disagreement. Snapshot rows retain the bounded API evidence needed to reproduce each predicate, including applicable policy/rules, required-check identity/results, CODEOWNERS result and merge state.

Precedence for several simultaneous failures: unauthenticated/untrusted transport fails before domain evaluation; unlinked GitHub `Bot` (its attempt binds the immutable GitHub actor ID in place of an identity link), or a linked `Bot`/non-human principal without a matching current Workspace allowlist entry in a `github_attestation`-mode repository → `bot-rejected`; binding failure → `binding-mismatch`; any remaining unmet/unknown predicate → `requirements-unmet`. Report all safe predicate reasons, but exactly one primary status/code. Infrastructure errors retain their transport diagnostics and never become a satisfied domain result.

Codes outside the result union: T2's installation permission-health observation code `attestation.permission_profile_mismatch`, and the refusals `gate.policy_missing` (first raised by T4's mode mutation, so the registry tags it E8.1.T4, then by T5's attested evaluator; no `repository_gate_policies` row, the existing E5 gate policy that is distinct from the T4 approval-source policy; checked first; attested evaluation only, a deliberate departure from the shipped absent-row `advisory` default because an attested approval needs an explicit gate policy, while native evaluation keeps deriving `advisory`) and `governance.attestation_not_current` (referenced attestation not `valid_current`). Both refusals stop evaluation before a gate decision is written; they are not `adoc.gate_result.v0` reasons and never replace `gate.approval_missing`, which stays the `approval_required` reason in both modes, including an attested-mode head that references no attestation, native approval or break-glass receipt (no review yet, or only a rejected attempt).

Registry work covers the new attestation/snapshot/setting receipt/result envelopes and every emitted code. Flip existing `attestation.bot_approver_rejected` and `action.attestation_bot_rejected` rows when their implementation/tests land; do not duplicate them. The registry's actual implemented-not-released status is `unreleased`, not a new `implemented` value. Do not mark any surface shipped merely because tests pass.

## 5. E8.1.T2 — authenticated fail-closed validation

**Outcome:** Cloud fetches GitHub facts with the repository's installation identity and evaluates every required predicate independently. Caller booleans, partial pagination and inaccessible settings cannot produce positive authority.

**Affected code:** new Cloud `src/lib/github-approval-attestation.ts` plus tests; existing `github-app.ts`, `github-installation-connection.ts`, permission-observation SQL plus one new forward migration for attestation permission-health observations, recorded only through `record_github_approval_attestation_permission_observation`, webhook refresh handling and T1 admission/gate integration. Reuse bounded fetch/timeout/token-revocation helpers. No generic connector abstraction, new queue system or independent CODEOWNERS parser.

**Provider facts, verified 2026-09-21:** review listings are chronological/paginated and expose reviewer, state, `commit_id` and submission time ([GitHub reviews API](https://docs.github.com/en/rest/pulls/reviews)); classic protection reads require repository Administration read permission ([protection API](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection)); the branch-rules endpoint returns applicable active repository/organization rules ([rules API](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch)). GraphQL `reviewDecision` is aggregate review state, while `mergeable` concerns merge conflicts; neither alone certifies every requirement ([pull-request reference](https://docs.github.com/en/graphql/reference/pulls)).

**Permission delta:** add explicitly scoped read capabilities for PR reviews, check runs/statuses, contents/CODEOWNERS and protection/rules as required by the chosen endpoints. Current token helper accepts only a limited permission set and the current audited installation manifest is actions/contents/metadata read; both must be versioned together. Request installation reconsent rather than accepting unobserved grants. Keep ingestion/read and publication/write App identities separate. Existing native-mode installations must not suddenly require attestation-only permissions. Missing consent/protection access yields unmet/unknown; no downgrade to unprotected success. Cloud records an insufficient observed installation permission profile as the permission-health observation code `attestation.permission_profile_mismatch`, which admits no attestation but sits outside the `AttestationFailure` union and the four-status projection and is never rendered by the Action; a permission-denied attestation result stays `attestation.requirements_unmet`. Tokens never enter Action output, snapshots or logs.

**Truth table:** start from one all-valid human fixture; mutate only the indicated input, including null/unknown variants. Every failure must prevent a stored accepted attestation and prevent a passing approval gate.
