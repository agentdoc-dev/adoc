A Cloud-disconnected repository keeps today's bytes.

## 2. Domain decisions and shared contracts

### D1 — connected-only reference block (accepted 2026-09-23)

The reference block, resolver trailer and Cloud delivery report exist only for a Cloud-connected repository. Disconnected delivery stays byte-for-byte compatible with `v2.0.0-alpha.21`. "Connected" is decided by one explicit root-action input (T1, `cloud-proposal-resolver`), default empty; no environment sniffing.

### D2 — Action produces, Cloud validates, nobody repairs

Action owns block rendering and its versioned wire schema `adoc.git_proposal_references.v0`. Cloud validates every field against stored evidence and records the outcome as an append-only attempt beside the immutable Proposal Record. Cloud never manufactures a field, edits a PR body, or re-renders the block. A rejected delivery report leaves the accepted proposal version untouched. The registry wording "rejects a proposal record" is clarified in Task A to "rejects the delivery association and retains the diagnostic on the proposal record" without weakening rejection.

### D3 — delivery is not writeback and not approval

Both paths reuse existing `deliver.sh` mechanics (sandbox `check_and_build`, ownership markers, `--force-with-lease`, `restore_proposal_branch`). A draft proposal never acquires an E6.5 managed origin version, `writeback_records` row or `source.writeback` grant. A delivery record never inserts an approval, governance, verification, promotion or effectivity event; `approval_required` continues to evaluate only `approval_records` / `github_approval_attestations` through `private.evaluate_gate_v0`.

### D4 — narrow operation, existing permission

The delivery report is a new `/api/v1` operation `proposal_delivery`, scoped by the existing `service_credentials.operations` array (`private.api_v1_request_authority_is_current` already requires `p_operation = any(credential.operations)`). No new permission primitive: the authorization check reuses `knowledge.propose` grants for the same principal that proposed, because reporting a delivery of one's own proposal grants nothing beyond it. Credentials minted before E8.2 do not carry `proposal_delivery` and therefore cannot call the new route.

### D5 — three heads, one predicate

H is the assessed source head recorded in `assessment_ingestions`; D is the delivered commit; the observed head is whatever the provider reports at validation time. The assessment is never relabelled as an assessment of D. Currentness (T2):

- `commit`: observed source PR head = D, D has exactly one parent H, and the observed `compare/H...D` changed-path set equals the proposal's bound source paths exactly (no extra, no missing path).
- `pr`: observed source PR head = H, Action-owned knowledge PR head = D, D has exactly one parent H, same changed-path rule; fork-origin sources keep H's repository identity while D lives in the base repository.
- Both: every `affected_objects` hash must equal Cloud's own recomputation from the canonical proposal (`private.proposal_graph_v6_content_hash`), and the report's assessment ingestion must still be `private.current_proposal_assessment_ingestion(p_workspace_id, p_value)` for the change request at admission time. Cloud does **not** recompile D's bytes; it records each changed blob SHA at D on the attempt for audit (limitation, §11). A newer accepted assessment after acceptance does not rewrite the attempt: staleness after acceptance is a derived read (`status: stale`, T5) computed from the accepted delivery's version versus the current ingestion, never a second attempt row. A transiently absent or partial observation is a retryable `503` with nothing persisted, never accepted; a definitive provider answer is a refused `ingest.digest_mismatch` attempt (D8, [`E8.2-FOLLOWUP-PLAN.md`](E8.2-FOLLOWUP-PLAN.md)). The report's `assessed_head_sha` must equal the ingestion's stored `head_revision`.

### D6 — resolver link is deterministic

Git → Cloud links cannot depend on a Cloud id minted after the commit. The resolver key is (Workspace, proposal-set digest): `proposal_record_versions` has `unique (workspace_id, proposal_set_digest)`, and Action already computes the same digest (`set_sha` in `deliver.sh`, `proposalSetDigest` in Cloud; parity covered by `proposal-action-parity.integration.test.ts`). Frozen path contract, used by T3 and served by T5:

```text
# Browser permalink (session cookie; redirects to /sign-in when unauthenticated)
https://<cloud-origin>/workspaces/<workspaceId>/proposals/<proposal-set-digest-hex>
# Session JSON read (same auth as src/app/api/workspaces/[workspaceId]/approvals/route.ts)
GET https://<cloud-origin>/api/workspaces/<workspaceId>/proposals/<proposal-set-digest-hex>
```

`<proposal-set-digest-hex>` is the 64 lowercase hex characters after `sha256:`. The root-action input `cloud-proposal-resolver` is the prefix `https://<cloud-origin>/workspaces/<workspaceId>`; Action appends `/proposals/<hex>` and never a token. Cloud → Git links are rendered from stored provider identity: `https://github.com/<owner>/<name>/commit/<D>` and `/pull/<n>` using `workspace_repositories.owner/name`.

### D7 — proven-unprotected branch is writable (owner, 2026-09-25)

A connected `commit`-mode delivery on a branch whose authenticated observation proves **no** protection at all (no classic protection, no rulesets) is allowed. Proven absence is a known state, not an unknown one; the lease, exact-head and sandbox checks in section 6 still apply. Only an unknown or bypassable profile refuses. This reads the milestone's "branch-protection preconditions" as "the observed protection profile is known and not bypassable", recorded beside D1 in `MILESTONES.md`.

Existing codes reused exactly: `delivery.reference_missing`, `delivery.reference_stale`, `delivery.fork_branch_read_only`, `ingest.digest_mismatch`, `ingest.duplicate_delivery`, `ingest.envelope_version_unsupported`, `api.idempotency_conflict`.

**Block bytes (T1 freezes; illustrative values).** One block per PR body; HTML-comment delimited; compact JSON, key order as shown, UTF-8, no trailing newline inside the markers, ≤ 64 KiB:

```text
<!-- AgentDoc-Proposal-References:v0 -->
{"schema_version":"adoc.git_proposal_references.v0","source_pr":{"repository_id":"123","number":42},"source_head_sha":"<40 hex>","assessment_receipt_digest":"sha256:<64 hex>","affected_objects":[{"object_id":"task.example","content_hash":"sha256:<64 hex>"}],"proposal_set_digest":"sha256:<64 hex>"}
<!-- /AgentDoc-Proposal-References:v0 -->
```

Rules: `source_pr.repository_id` is the numeric base-repository id (`GITHUB_REPOSITORY_ID`) even for a fork-origin PR; `affected_objects` is sorted by `object_id`, non-empty, no duplicates, one **post-patch** semantic hash per manifest target that was actually written, read from the `check_and_build final` graph (`deliver.sh:383`) into a **new** retained file `delivery-affected-objects.json`. The existing `delivery-object-set.json` (`deliver.sh:325–331`) is the whole **initial** graph checked against `context.object_set_sha256` and stays untouched. Pre-edit hashes stay in `adoc.proposal.v0.content_bindings`; `assessment_receipt_digest` is the digest of the finalized `adoc.pr_assessment_receipt.v4` bytes (`$OUT/receipt-sha256`), not the assessment digest `write_pr_body()` prints today; `proposal_set_digest` is `set_sha`, and a run with no proposal record (`set_sha` empty, `deliver.sh:423`) emits no block and reports the typed skip `references.skipped: no_proposal_record`. Unknown keys, duplicate keys, a second marker pair, or any missing field is a parse failure.

Closed consumer type (proposed, `src/lib/contracts/git-proposal-references.ts`):


**Delivery report (T2 freezes).** POST `/api/v1/workspaces/[workspaceId]/proposal-deliveries`, `Idempotency-Key` required, bearer service credential with operation `proposal_delivery`:

```ts
// Proposed wire shape, agentdoc.cloud.proposal_delivery.v0
type ProposalDeliveryV0 = {
  schema_version: "agentdoc.cloud.proposal_delivery.v0";
  repository: { provider: "github"; external_repository_id: string };
  change_request: { system: "github_pull_request"; id: string };   // source PR number as text
  proposal_version_id: string;              // uuid returned by upload-cloud-proposal.sh
  proposal_set_digest: string;
  assessment_receipt_digest: string;
  assessed_head_sha: string;                // H; must equal assessment_ingestions.head_revision
  project_prefix: string;                   // `git rev-parse --show-prefix` at delivery, "" at repo root
  mode: "commit" | "pr";
  delivered_commit_sha: string;             // D
  knowledge_pull_request_number: number | null;   // pr mode only
  references_block: string | null;          // Action's copy of the block bytes, pr mode only
  references_block_digest: string | null;
};
```

Idempotency key: `sha256(printf '%s\n%s' proposal_set_digest request_digest)` where `request_digest` is the digest of the submission bytes, exactly as `upload-cloud-proposal.sh:112–114` derives its key. Same key with different bytes is refused `409 api.idempotency_conflict`. Responses (the existing `/api/v1` envelopes; success in the ingestion-result envelope, refusals as `error: {code, message, remediation?}`):

- `202` payload `{status:"accepted", code:null, delivery_id, original_code:null}`; a same-key replay of any retained attempt returns `200` with `status:"duplicate"`, `code:"ingest.duplicate_delivery"`, the original attempt's `delivery_id` and `original_code` set to the original attempt's code (`null` only when that attempt was accepted). The Action reports `cloud_sync: ok` only for `202`, or for a `200` duplicate whose `original_code` is `null`; a replayed refusal fails with its `original_code` and never marks the attempt accepted.
- `422` with a refused attempt's `code` (`delivery.reference_missing`, `delivery.reference_stale`, `ingest.digest_mismatch`, `ingest.duplicate_delivery`). An unknown reference-block version adds `remediation.remediation_code: "ingest.envelope_version_unsupported"`.
- `422 ingest.envelope_version_unsupported` with `remediation.supported_versions` for an unknown report version.
- `503 delivery.provider_unavailable`.
- The existing `400 api.invalid_request`, `403` authorization refusals and the non-enumerating `404 {error:"not_found"}` for an unknown proposal or a foreign Workspace.

Trust source: in `pr` mode Cloud parses only the **provider-observed** PR body. The supplied `references_block` must equal the observed block byte for byte, otherwise `ingest.digest_mismatch`; it exists so the attempt row retains what the Action believed it published.

```sql
-- inside public.ingest_proposal_delivery; v_obs is the server-side observation.
-- `is distinct from` everywhere: a missing key or NULL current ingestion must read
-- as stale, never fall through to accepted.
if p_assessed_head is distinct from v_ingestion.head_revision   -- assessment_ingestions.head_revision, 20260825020000:120
then v_code := 'ingest.digest_mismatch';   -- caller may not relabel the assessment onto another head
elsif v_version.assessment_ingestion_id is distinct from
     private.current_proposal_assessment_ingestion(p_workspace_id, p_value)  -- (uuid, jsonb), 20260903000000:2483; p_value is the proposal value jsonb

   or (p_mode = 'pr' and (v_obs->>'source_head' is distinct from p_assessed_head
        or v_obs->>'knowledge_head' is distinct from p_delivered_commit))
then v_code := 'delivery.reference_stale';
elsif (select coalesce(jsonb_agg(path order by path), '[]') from jsonb_to_recordset(v_obs->'changed') as c(path text))
      is distinct from v_bound_paths
then v_code := 'ingest.digest_mismatch';
end if;
```

### Migration, rollout and rollback

Forward migrations only; no edit of applied migrations, no backfill of old proposal/approval/receipt bytes or existing PR bodies. Historical deliveries have no E8.2 association and read as `missing`, never green. Release order: registry rows and Cloud consumer (T2 tables, route, read route) first; then Action producer/uploader behind the empty-default `cloud-proposal-resolver` input; then enable per connected repository by minting a credential with `proposal_delivery` and setting the input. Rollback: clear the input (Action returns to today's bytes), revoke the credential; retained attempts stay readable; never delete history or mark refused attempts accepted; never reset a successful source commit as transport recovery.

## 11. Known limitations and open questions

- **Provider observation cost:** T2 performs three to four GitHub reads per report with the installation token; acceptable at proposal volume, revisit only on measured rate-limit pressure.
- **Delivered bytes are not recompiled by Cloud:** T2 proves parentage, head identity, the exact changed-path set and the proposal's own hashes, and retains blob SHAs at D; it does not compile D's files. A same-path, different-content commit is caught only by the Action's sandbox replay and by E8.1/E6.5 gates downstream. Recompilation in Cloud is a candidate for E8.3 if the retained blob SHAs show drift in practice.
- **Project prefix is caller-supplied:** no Cloud table stores the Action working directory; T2 accepts `project_prefix` from the report and only checks it is a common prefix of the observed paths. In a monorepo with sibling projects that share relative paths (`a/docs/x.md`, `b/docs/x.md`) a report could name the sibling prefix and pass the path check; heads, parents and hashes are still observed, and the no-recompile limitation above already bounds content. Binding the prefix to stored evidence (for example an assessment-ingestion field) is deferred until an ingestion contract change is otherwise needed.
- **Proposal-version key:** T2 adds `unique (workspace_id, id, proposal_set_digest)` to `proposal_record_versions` for the delivery FK; `api_v1_requests` is referenced through its existing four-column unique key (`20260825000000:37`).
- **Bootstrap runs** (no source PR) have no `source_pr`; they stay outside this contract by construction and report `missing` in Cloud.
- **Live qualification:** branch-protection profile and PR-body publication are proven against mocked responses; qualify on the owned controlled repository before setting `cloud-proposal-resolver` on a real connection (same posture as E8.1 §11).
