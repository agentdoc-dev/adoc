## 2. Decisions

### D8 — definitive provider answers are refused attempts, not outages (owner, 2026-09-25)

A definitive answer is one the same request bytes can never turn into a success: HTTP 404 on any of the four observed resources **after one short in-route retry**, or a resource body over `MAX_PROVIDER_BYTES` (8 MiB). It is admitted, registered (`register_api_v1_request_with_transmission`) and retained by `public.ingest_proposal_delivery` as a refused attempt with code **`ingest.digest_mismatch`** and a closed reason in `observation.provider_reason`. Every other failure — 5xx, 429, 403, 401, 422, redirect, timeout, network error, malformed JSON, missing app credentials, installation or token — stays `503 delivery.provider_unavailable` with nothing persisted.

Why reuse `ingest.digest_mismatch` instead of a new code: the attempt table's `code` check (`20260925000000:19–20`), the route's `REJECTED` set (`route.ts:44–49`), the uploader's typed-code list (`upload-cloud-proposal-delivery.sh:240–243`), the registry row and the guard test are all closed on the same four codes; a new code touches DDL, route, Action, registry and guard for no consumer gain. Semantically the report names provider identity (a PR number, a commit, a range) the provider says does not exist, which is exactly the registry's E8.2 case "disagree with stored evidence or the provider observation" (row 670). The retained reason keeps it distinguishable, mirroring how the over-300-files refusal is retained as `observation.changed_over_bound` (plan §T2 step 3 calls it `changed_paths_over_bound`; the code stores the boolean — no change to that path).

Closed vocabulary (`route.ts` and the RPC both validate it):

```text
provider_reason ∈ (source_pr|knowledge_pr|delivered_commit|compare)_(not_found|over_byte_bound)
```

Precedence when several resources fail definitively: the first in the order `source_pr, knowledge_pr, delivered_commit, compare`; one reason per attempt. A transient failure on any resource wins over a definitive one on another (the request is still retryable), so the route checks transient first.

The 404 retry: GitHub reads can lag a push by a few seconds, and the Action reports only after `finalize.sh` and the receipt, so lag is unlikely but not impossible. The route re-fetches only the 404'd resources once after `NOT_FOUND_RETRY_MS = 2_000` with a 5 s timeout; a second 404 is definitive. A refusal consumes the idempotency key (unchanged E8.2 rule): an identical Action retry gets `200 duplicate` with `original_code: "ingest.digest_mismatch"` and fails typed — the uploader already handles that (`upload-cloud-proposal-delivery.sh:221–247`, proven by `test/assessment-ingestion.sh` mode `duplicate_refused` at 644–646/757–759). No Action change for F1.

Compare `422` / "no common ancestor": D must have exactly one parent H, so an unrelated D is caught as `delivery.reference_stale` once the commit read succeeds; a compare that answers 404 for a range whose commits exist is still definitive (`compare_not_found`). 422 cannot be caused by validated input (both SHAs are 40 hex) and is documented by GitHub as "validation failed, or the endpoint has been spammed", so it stays transient. Only the rules/branches semantics in D9 were re-verified through Context7 on 2026-09-25; the decision does not depend on GitHub's exact status list beyond 404.

Non-enumeration is unchanged: the route already answers `404 not_found` for an unknown or foreign version and for a repository/PR identity other than the ingestion's (`route.ts:271–304`) before any provider call, so a provider 404 only ever concerns the caller's own bound identity.

### D9 — only rulesets that apply to the branch guard delivery (owner, 2026-09-25)

`observe_protection()` fetches ruleset details only for the ruleset ids that `GET repos/{r}/rules/branches/{branch}` (paginated) reports, and requires the detailed set to equal that id set. An applying ruleset must be `enforcement: "active"` with `bypass_actors` present and empty; an omitted `bypass_actors` (org rulesets under a token that cannot read it) still refuses as unknown; a detail whose id or enforcement disagrees with the rules listing refuses as unknown. Rulesets that do not apply to the branch — in any enforcement mode, with any bypass list — no longer refuse and are no longer fetched. The `rulesets?includes_parents=true` listing is dropped. Classic-protection handling, the second observation before push and `protection_drift` are unchanged.

GitHub docs (Context7, 2026-09-25, [repository rules](https://docs.github.com/en/rest/repos/rules)): "Returns all active rules that apply to the specified branch … Rules in rulesets with `evaluate` or `disabled` enforcement statuses are not returned", and the branch need not exist. `GET repos/{r}/rulesets/{id}?includes_parents=true` already serves organisation rulesets (the merged code relies on it). Whether `rules/branches` is complete for organisation rulesets under a non-admin installation token is still unverified live; it stays the E8.2 §11 activation item.

D7 is clarified, not changed: "the observed protection profile is known and not bypassable" means the profile of the rulesets that apply to the branch. `MILESTONES.md:953` and plan §T3 step 2 ("and each ruleset", line 309) get that wording in Task F3.

## 7. Migration and rollback

Cloud: one forward migration re-creating two functions from their live definitions; no table change, no backfill. Historical attempts are unaffected; rows never gain `provider_reason`. Rollback is a further migration restoring the previous bodies; the route must roll back with it (a route sending `provider_reason` to the old RPC yields `reference_stale`, still a refusal, never an acceptance). Action: `deliver.sh` change is inside the connected gate; rollback is the previous release tag. Adoc: docs only.

## 8. Risks

- **Lag beyond one retry.** If GitHub still answers 404 more than ~2 s after the Action's push, the refusal is permanent for those bytes and the delivery reads `pending` until a new report with different bytes (a new D). Mitigation: the Action reports after finalize and receipt (seconds later); `NOT_FOUND_RETRY_MS` is one constant. Accepted by the owner.
- **Route duration.** Worst case adds ~7 s (2 s wait + 5 s retry timeout) to a route that already allows four 10 s reads. `vercel.json` sets no function duration; internal routes export `maxDuration` (e.g. `github-check-retries/route.ts:6`). If the deployed default is under 30 s, F1.2 adds `export const maxDuration = 60` — owner to confirm the Vercel plan default before merge (open item).
- **`rules/branches` completeness for org rulesets** under a non-admin installation token remains docs-only; the drift re-observation and the omitted-`bypass_actors` refusal bound the damage. Live qualification stays the activation item (E8.2 §11).
- **Reason mixed into a human string.** `attempts[].reason` carries the token in parentheses; U-slice screens may later map it. The schema is unchanged.
